============================================================
1) OBJETIVO DO PROJETO
============================================================

O projeto é um site pessoal de compartilhamento de arquivos, auto-hospedado, com interface simples, rodando em Node.js, acessível pelo próprio domínio do usuário.

Objetivo funcional:
- Upload de arquivos do computador do usuário.
- Outra pessoa pode acessar o site de outro lugar e baixar arquivos.
- O usuário quer controle sobre o que é publicado.
- Interface básica primeiro, depois melhorias.
- O usuário está aprendendo do zero e prefere instruções claras e guiadas.

Visão de longo prazo:
- Melhorar a interface.
- Adicionar drag and drop.
- Adicionar login de verdade.
- Melhorar a segurança.
- Talvez notificações.
- Talvez metadados de arquivo (tamanho, data, etc.).

============================================================
2) ESTADO ATUAL DA APLICAÇÃO LOCAL
============================================================

Arquitetura local discutida:
- Backend: Node.js com Express.
- Uploads: Multer.
- Frontend: HTML/JS puro.
- Armazenamento local em pastas.
- Sem banco de dados.
- Sem login ainda.
- Sem restrição de tipo ou tamanho de arquivo por enquanto.

Padrão importante de organização do código:
- Código do navegador deve ficar no arquivo public/index.html.
- Código do servidor deve ficar no arquivo server.js.
- O usuário já foi orientado antes a não colocar JavaScript de navegador dentro do server.js.

Estrutura de fluxo do app:
- Arquivos enviados primeiro para uma pasta temporária.
- Só depois de aprovação eles vão para a pasta pública.
- O usuário aprova manualmente os arquivos que quer publicar.
- Rejeitar apaga da pasta temporária.
- Deletar remove da pasta pública.
- Download deve forçar o arquivo a baixar, não abrir no navegador.

============================================================
3) BACKEND DISCUTIDO
============================================================

Estrutura de backend que foi discutida e considerada funcional:

- require express, multer, path, fs
- app = express()
- multer diskStorage com destination "./temp"
- filenames usando Date.now() + path.extname(file.originalname)
- app.use(express.static("public"))
- app.use("/files", express.static("uploads"))

Rotas discutidas:
- POST /upload -> salva em temp
- GET /list -> lista arquivos aprovados em uploads
- GET /pending -> lista arquivos pendentes em temp
- GET /approve/:name -> move de temp para uploads
- GET /reject/:name -> remove de temp
- GET /delete/:name -> remove de uploads
- GET /download/:name -> força download do arquivo

Servidor:
- app.listen(3000)

Detalhe importante:
- Download deve usar res.download para forçar o comportamento de download.

5) REDE, CGNAT E ACESSO EXTERNO
============================================================

Situação de rede:
- O usuário está atrás de CGNAT.
- O roteador ZTE F670L não permitiu port forwarding normal.
- Por isso a recomendação correta foi não expor a máquina diretamente pela porta do roteador.

Solução adotada/recomendada:
- Cloudflare Tunnel.
- O domínio vai apontar para o serviço local via tunnel.
- O acesso público não deve depender de abrir porta no roteador.

Fluxo desejado:
- Servidor local rodando em http://localhost:3000
- Tunnel apontando para localhost:3000
- Domínio público servindo o site sem porta aberta no roteador

7) HOMEHOST: O QUE ACONTECEU
============================================================

A Homehost foi usada inicialmente, mas deu problema grave no processo de registro do domínio.

Resumo do problema:
- O usuário comprou o domínio pela Homehost.
- Durante muito tempo o domínio não aparecia no WHOIS.
- O domínio continuava disponível para compra em outros lugares.
- DNS checker e nslookup não retornavam nada útil.
- O suporte inicialmente respondeu como se fosse apenas configuração de DNS errada.
- Depois, em outra mensagem, disseram que o registro do domínio havia sido concluído.
- Na prática, isso não batia com os testes externos feitos pelo usuário.

Depois de insistência:
- O suporte acabou orientando o usuário a pedir reembolso.
- Isso sugere que o registro não estava corretamente concluído ou que houve falha grave no processo deles.

Impressão deixada:
- A empresa é legítima, mas o atendimento e o processo de registro do domínio falharam de forma feia nesse caso.
- O usuário ficou frustrado com a demora de 2 meses e com a interface/fluxo ruins.
- Houve respostas automáticas ou pouco úteis do suporte.
