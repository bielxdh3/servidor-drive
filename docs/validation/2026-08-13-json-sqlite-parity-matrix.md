# Root.ark JSON/SQLite parity matrix — 2026-08-13

## Purpose and evidence boundary

This is the Phase C source-backed parity matrix for repository `bielxdh3/root.ark`, branch `cdx/rootark-roadmap`, local base SHA `28747c6ebdac873650e2d5a3c6193824e7cc9985`. It is measurement planning, not a parity claim and not an authorization to migrate or remove JSON fallback.

The current design is selected by `server.js:shouldUseDatabase()`, `shouldReadJsonFallback()`, and `shouldWriteLegacyJson()`. SQLite resolves from `DATABASE_URL` or `data/rootark.sqlite`, enables WAL, foreign keys, and a busy timeout in `db/index.js`; JSON remains a fallback/legacy-write path. Repository writes generally replace a complete logical collection inside `runWrite()` transactions, while JSON writes are direct file writes except where a domain-specific lock/temporary rename exists. The two modes therefore need semantic, ordering, failure, and restart measurements before any policy change.

Evidence labels used below:

- **Measured behavior**: an existing executable test reached its assertions and its result is recorded in the evidence sources.
- **Source mapping**: code and schema inspection identifies the path, but no equivalent executable parity assertion exists.
- **Unverified**: the relevant behavior, failure mode, or cross-mode equivalence is not established; an environment blocker is recorded separately when applicable.
- **Owner decision**: a product or operational choice that code evidence cannot settle.

“Delete” means the public/current lifecycle operation where applicable. Several repository adapters implement full-snapshot replacement (`DELETE` then insert/upsert) rather than a repository-level single-row delete; that distinction is material to rollback and concurrent-writer analysis.

## Cross-cutting parity questions

1. **Fallback precedence:** `server.js` can read SQLite, fall back to JSON when the SQLite collection is empty or unavailable, and optionally dual-write legacy JSON. A probe must record whether an empty SQLite collection is authoritative or merely a migration gap; do not silently turn this into a product decision.
2. **Snapshot replacement:** permissions, pending uploads, links, expirations, versions, encryption, analytics, audit, and action history use whole-collection replacement in SQLite helpers. Compare a failed write, duplicate key, and concurrent writer in both modes before declaring CRUD parity.
3. **Ordering:** JSON insertion order and SQLite query order differ for several surfaces. Exact order is part of API behavior where routes expose arrays; otherwise the owner must decide whether order is meaningful.
4. **Foreign keys and implicit folders:** SQLite repository helpers call `ensureRootFolder`/`ensureFolderId`; JSON accepts keys without a relational folder row. A parity fixture must distinguish a compatibility normalization from an authorization policy.
5. **Filesystem coordination:** uploads, quarantine, trash, backups, encrypted bytes, cloud cache, and WebDAV journals cross the metadata boundary. A database transaction alone cannot prove byte/payload rollback.

## Smallest executable probe set

Add probes in a later implementation packet only after dependencies are available and only with disposable runtime roots:

- one fixture builder that writes the same logical seed into JSON mode and SQLite mode;
- one round-trip comparator for normalized public objects, explicit ordering, omitted/default fields, and uniqueness;
- one restart/reopen comparator for each surface in the matrix, beginning with users, folders, pending uploads, permissions, links, expirations, versions, encrypted metadata, analytics, audit, history, and trash;
- one failure injector for repository snapshot replacement that proves the prior committed state remains readable after a failed transaction, plus the JSON-mode limitation where no equivalent transaction exists;
- one migration fixture that runs JSON → SQLite twice, compares counts and normalized records, and verifies the source/backup remains intact;
- one cross-resource probe for pending/quarantine/trash/backup metadata versus bytes, explicitly reporting non-atomic windows instead of choosing a new policy;
- one backup/restore reopen probe for configured database paths, WAL/SHM handling, and journal cleanup;
- one session-generation probe across JSON restart and SQLite soft-delete/recreate, reusing existing auth assertions rather than duplicating route tests.

Do not add probes that require production data, live ClamAV/S3/Google Drive, an OS WebDAV mount, credentials, or a product decision about encryption, quarantine release, or JSON fallback precedence.

## Recommendation and open decisions

Recommendation only: after parity and migration acceptance, make SQLite the safer mandatory production target; retain JSON only as an explicitly bounded migration/legacy fallback until the owner approves removal or continued support. This is not owner approval and does not change `DB_ENABLED`, fallback, or legacy-write behavior.

Still open: full row/shape parity; ordering guarantees; JSON crash consistency; migration idempotence across every named surface; rollback/disaster-recovery for metadata plus bytes; backup/trash/quarantine cross-resource recovery; long-running migration performance; external-provider/cloud parity; and the mandatory-production-SQLite decision. Realtime remains intentionally non-persistent. D-008 retention and D-003/D-009 zero-knowledge/encryption/quarantine decisions remain product/security constraints, not implementation conclusions.

No runtime code, tests, package files, plan-tree, architecture, issue ledger, workflow, production data, credentials, or remote state were changed by this packet. Remote CI and production behavior are unconfirmed.
